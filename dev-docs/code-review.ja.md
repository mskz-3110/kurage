# コードレビューガイド

## レビューの目的

- バグ、動作の退行、データ損失、セキュリティ上の問題、運用上のリスクを見つける。
- 指摘はコードの正しさと利用者への影響を優先し、好みだけのスタイル変更は指摘しない。
- 変更範囲を確認し、依頼された対象と関連する呼び出し元・テストも必要に応じて調べる。

## 確認する観点

- 正常系だけでなく、空・境界値・不正入力・失敗時の動作が妥当か。
- 非同期処理、リソース解放、一時ファイル、cwd、プロセス共有状態が安全に扱われているか。
- APIの互換性、既存動作への影響、エラーや例外の伝播が適切か。
- 変更の重要な動作をテストしているか。テストが実装詳細に過度に依存していないか。
- 型や設定の制約、Node.jsとBunなど対象ランタイムの差異を踏まえているか。

## 指摘の基準

- 指摘は重要度の高い順に並べ、対象ファイルと行を示す。
- 各指摘に、問題となる条件、発生する結果、影響を簡潔に含める。
- 実際に再現またはコード上で根拠を確認できる問題に絞る。推測に基づく場合は前提を明記する。
- 同じ根本原因から派生する問題は、可能な限り一つにまとめる。
- 改善提案と不具合を区別する。任意の可読性・保守性改善を重大な問題として扱わない。
- 問題が見つからない場合は、その旨を明記し、残る検証不足やリスクがあれば併記する。

## 検証

- 変更に関係するテストを確認し、必要に応じてテストを実行する。
- 実行できなかったコマンドや環境上の制約は、レビュー結果に明記する。
- カバレッジの数値だけで品質を判断せず、重要な分岐や失敗時の振る舞いが検証されているかを見る。

## 報告形式

- レビュー結果はリポジトリルートの`.review_code.md`に出力する。ユーザーが別の出力先を指定した場合は、その指定を優先する。
1. 指摘事項を重大度順に列挙し、各項目にファイル・行、条件、影響を記載する。
2. 必要なら、確認した前提や未解決の質問を記載する。
3. 指摘がない場合は明示し、テスト未実行などの残余リスクを記載する。
4. 変更概要は指摘より後に、必要な場合だけ簡潔に記載する。
